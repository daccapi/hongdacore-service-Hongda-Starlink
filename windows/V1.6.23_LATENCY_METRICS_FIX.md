# V1.6.23 延迟指标修复

## 问题

V1.6.22 把 Clash API `delay` 直接显示为节点延迟。该值实际包含新建节点 TCP/TLS/
WebSocket 隧道、目标站 TLS 握手以及 HTTP 首包，并不是节点服务器 RTT。

现场只读采样中，同一节点服务器 TCP RTT 中位数约为 212 ms，而完整代理 URLTest 为
826–1499 ms。此前 UI 显示 1000 ms 以上，属于指标名称与数据语义不一致。

## 修复

- 节点延迟：对节点服务器执行三次 TCP 建连采样并显示中位数。
- 代理传输建立：Core 记录 `Outbound.DialContext` 完成耗时，API 返回
  `connectDelay`。
- 完整代理链路：继续完成测试 URL 的 TLS/HTTP 请求，兼容字段 `delay` 与新增字段
  `totalDelay` 都返回该总耗时。
- 只有完整代理链路成功才标记 `代理可用`；单独 TCP 成功仍只标记 `TCP可达`。
- 日志同时输出节点 RTT 与完整代理探针，避免把更小的数字误当作代理可用证明。

## API 示例

```json
{
  "delay": 1091,
  "totalDelay": 1091,
  "connectDelay": 618,
  "status": 204
}
```

Clash 兼容字段 `delay` 的含义没有改变，因此外部控制端不会因本次修复得到虚假的较小值。
